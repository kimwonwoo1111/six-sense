## 1. 무엇을 수요로 볼 것인가 — 차량 대수 → 150m 점유율

**문제.** 처음에는 방향별 차량 대수를 세어 수요로 삼았습니다. 그런데 대수는 카메라 각도, 차량 겹침, 프레임 순간값에 민감하고, "몇 대"가 도로가 실제로 얼마나 막혔는지를 잘 나타내지 못했습니다.

**해결.** 정지선에서 뒤로 150m 구간의 점유율(구간 안 차량 길이 합 ÷ 구간 길이, 차로 평균)로 수요를 바꿨습니다. → [`occupancy_150m()`](../sumo_runner.py#L274)

**설계 포인트.** 입력 단위가 바뀌어도 배분 로직을 다시 쓰지 않도록 배분 코어 [`allocate_from_demand()`](../signal_allocation.py#L88)를 분리했습니다. 이 함수는 수요의 비율만 쓰기 때문에 파이썬 시뮬레이션(대수)과 SUMO(점유율)가 같은 코드를 씁니다.

```
파이썬 시뮬레이션:  BlockCounts(대수) ─ compute_demand() ─┐
                                                          ├─▶ allocate_from_demand() ─▶ {현시: 녹색초}
SUMO 연동:         occupancy_150m()(점유율 %) ────────────┘
```

## 2. 언제 측정할 것인가 — 순간값 → 빨간 구간 평균

**문제.** 처음에는 각 방향의 녹색 30초 전 한 순간의 점유율을 썼습니다. 같은 혼잡 방향인데도 찍는 순간에 따라 값이 크게 달라졌고(당시 관찰 예: 68% → 24% → 51%), 배분 시간도 사이클마다 출렁였습니다.

**버린 대안.**
- 측정 시점만 옮기기: 여전히 한 순간이라 근본 해결이 아닙니다.
- 매 스텝 전부 평균: 자기 녹색 동안 대기열이 빠지는 구간까지 섞여 수요가 낮게 잡힙니다.

**해결.** 대기가 쌓이는 시간은 그 방향이 빨간불인 동안입니다. 그래서 자기 녹색이 아닌 동안 10초마다 점유율을 재고, 녹색이 켜지는 순간 평균을 내 그 사이클 값으로 확정했습니다. 블록(3사이클)이 끝나면 사이클 값들을 다시 평균 냅니다.

**구현에서 신경 쓴 점.** 방향별로 상태를 따로 둡니다.

| 상태 | 역할 |
|---|---|
| `red_elapsed` | 현재 빨간 구간 경과 시간 |
| `next_sample` | 다음 샘플을 찍을 시각 |
| `red_samples` | 현재 빨간 구간의 샘플들 |
| `snap` | 이번 블록의 사이클별 값 |

루프 순서는 `매 스텝 샘플 → 신호가 바뀌면 녹색이 켜진 방향을 마감(평균·리셋) → 첫 현시로 돌아오면 사이클 +1, 블록 경계면 재배분`입니다. 이 순서가 어긋나면 샘플이 다른 사이클에 섞이기 때문에, 방향 1의 값이 `snap`에 들어간 뒤에 블록을 마감하도록 맞췄습니다. → [`sumo_runner.run()`](../sumo_runner.py#L302)

## 3. 어떻게 공정하게 나눌 것인가 — 최소 보장 · 비례 · 상한

**문제.** 수요에 정비례로만 나누면 한 방향이 몰릴 때 다른 방향은 신호를 거의 받지 못합니다.

**해결.** 모든 차량 현시에 최소 40초를 먼저 주고, 남은 시간만 수요 비례로 나눈 뒤, 80초를 넘지 않게 자르는 3단계로 정했습니다. 수요가 전혀 없으면 기준값으로 동작합니다.

**남은 과제.** 80초로 자른 초과분을 다른 방향에 다시 나누는 규칙은 아직 없습니다(코드의 TODO).

## 4. 어디서 검증할 것인가 ① — 실제 도로(OSM) → 직접 정의한 교차로

**문제.** 처음에는 실제 도로 교차로를 OSM에서 가져와 SUMO 네트워크로 변환했습니다. 그런데 이 교차로는 여러 노드가 넓게 묶인 복잡한 클러스터여서, 신호와 연동되는 횡단보도가 생성되지 않았습니다.

**해결.** 목적은 실제 도로 재현이 아니라 알고리즘 검증이었기 때문에, 4방향 3차로 대칭 교차로를 노드·엣지 파일로 직접 정의했습니다([`cross.nod.xml`](../cross.nod.xml), [`cross.edg.xml`](../cross.edg.xml)). 이렇게 하니 보도와 횡단보도까지 정상적으로 생성됐습니다.

## 5. 어디서 검증할 것인가 ② — 신호 프로그램 자동 생성

**문제.** SUMO가 기본으로 만드는 신호는 5현시 설계와 다릅니다.

**해결.** TraCI `setProgramLogic`으로 9단계(4방향 × 녹색·황색 + 보행) 프로그램을 코드에서 만들어 설치했습니다. 신호 상태 문자열은 제어 링크 구조에서 자동으로 만들고, 횡단보도 링크와 우회전 링크도 자동으로 찾습니다. 우회전은 모든 단계에서 양보 녹색을 줘서 한국식 우회전 상시 통행을 반영했습니다. → [`build_program()`](../sumo_runner.py#L220), [`build_right_turn_indices()`](../sumo_runner.py#L201)

교차로 형태가 바뀌어도 링크를 자동으로 읽기 때문에 신호표를 손으로 고칠 필요가 없습니다.

## 6. 무엇으로 성능을 판단할 것인가 — 지표 보강

**문제.** 초기에는 진입로의 정지 차량 수만 봤습니다. 그런데 신호를 잘못 줘서 차를 덜 들여보내면, 진입하지 못한 차는 대기열에 잡히지 않아 지표가 오히려 좋아 보일 수 있었습니다.

**해결.** 지표를 세 가지로 보강했습니다. → [`compare_runner.py`](../compare_runner.py)

1. **처리량 함께 집계**: 통과 차량 수를 같이 보고, 적응형 처리량이 고정식의 98% 미만이면 경고를 출력합니다.
2. **SUMO 표준 지연 `timeLoss`**: 완전 정지뿐 아니라 서행으로 인한 손실까지 포함합니다.
3. **워밍업 제외**: 첫 재배분 전 블록은 두 방식이 똑같이 동작하므로, 그 구간에 출발한 차량은 빼고 비교합니다. 워밍업 길이는 `3사이클 × (녹색 합 + 방향별 황색)`으로 자동 계산합니다(936초).

두 SUMO 인스턴스에 같은 차량 수요 파일을 넣고, `traci.switch()`로 번갈아 한 스텝씩 진행해 신호 방식만 다르게 비교했습니다.

## 7. 어떤 상황에서 비교할 것인가 — 시나리오 설계

**문제.** 교통량이 일정한 조건에서는 고정식과 적응형의 차이가 작았습니다. 적응형의 장점은 상황이 바뀔 때 드러나기 때문입니다.

**해결.** 30분마다 붐비는 방향이 북 → 동 → 남 → 서로 바뀌는 시나리오([`SCENARIO_SCHEDULE`](../signal_allocation.py))를 만들었습니다. 혼잡 등급은 도착률 범위로 정의하고, 포아송 도착과 시간 창별 강도 변동을 넣어 같은 등급이라도 사이클마다 몰렸다 뜸해지게 했습니다. 시드를 고정해 같은 입력이면 같은 결과가 나오도록 했습니다.

## 돌아보며 — 아직 남은 문제

- **비교 기준선**: 고정식은 보행 60초, 적응형은 보행 30초로 동작합니다. 보행 시간을 같게 맞춘 기준선으로 다시 비교해야 배분 방식만의 효과를 분리할 수 있습니다.
- **반복 검증**: SUMO 비교는 한 시나리오, 한 번의 실행입니다. 여러 시드로 반복해 분포를 확인해야 합니다.
- **설정값 확정**: 기준·최소·최대 녹색, 황색, 보행 시간은 실측 데이터로 정해야 하는 임시값입니다.
- **스필백**: 150m 밖까지 늘어난 대기열을 잡는 보조 지표가 필요합니다.
